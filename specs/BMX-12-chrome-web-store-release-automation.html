Automate the Chrome Web Store release

A refinement spec for bookmark-express-v3: turn the hand-run submission checklist in store/README.md into one command that bumps the version, builds the zip, regenerates the store art, validates the listing copy, and uploads the package to the Web Store as a draft — leaving only the steps the Web Store API genuinely cannot do.

Ticket: BMX-12 Phase: refinement Target: bookmark-express-v3 (Svelte + TS, MV3) Type: build / release tooling (no extension behaviour changes) Date: 2026-07-27
How to use this document. §1 answers the ticket's actual question — how much of this is possible? §2 is what exists today. §3–§7 are the spec the build session implements. §8–§11 are acceptance criteria, files touched, scope boundaries, and the decisions already signed off. Nothing in the repo has been changed by this document.

1. TL;DR — how much of the ticket is possible

Four of the five wishes are fully automatable. The one that is not is not a matter of effort — the Chrome Web Store API has no endpoint for listing metadata and never has. That is a permanent ceiling, not a gap we can close later.

Ticket wishVerdictWhy
Regenerate the demo images Automatable scripts/gen-store-assets.mjs already renders all four assets from the brand art and the built popup. The release command calls it. Getting the new PNGs into the store listing is a manual drag-and-drop — see the row below.
Update our description Partly The API cannot write the description, summary, screenshots, promo tile, category, or privacy justifications. Those are Developer Dashboard fields, full stop. What we can automate: keep the copy in store/listing.md as today, and have the release command emit each dashboard field as a separate paste-ready .txt, length-checked against the store's limits and cross-checked against the manifest. Pasting stays manual.
Build the zip as we do today Automatable npm run zip already does exactly this. The release command calls it unchanged, so the artifact is byte-for-byte the process we ship today.
Upload as a new draft release Automatable Web Store API v2 publishers.items.upload uploads a package against an existing item. Upload does not submit for review — the new version sits as the item's draft until something calls publish. That is precisely the ticket's ask, and it is one API call.
Near-zero-touch releases Achieved After this ticket a release is: run one command, then in the dashboard paste any changed text fields, drag any changed images, click Submit for review. When neither the copy nor the art changed — the common case for a bugfix release — the manual part collapses to a single click.
Two hard constraints the build session must design around.
  • API v1 dies 15 October 2026. The legacy googleapis.com/chromewebstore/v1.1 endpoints are deprecated with that hard cutoff — under three months from this spec's date. Most tutorials and several popular wrappers still target v1. Build against v2 (chromewebstore.googleapis.com/v2) only. Do not write a v1 code path "for now".
  • v2 cannot create items. Item creation was dropped from v2 deliberately, because a brand-new item still needs dashboard metadata before it can go anywhere. So the first submission of an item is always by hand; automation takes over from the second release onward. See §10 for what this means for v3 specifically.

2. What exists today

The release path is already half-built — it is just not joined up, and every step is invoked by hand from store/README.md's checklist.

PieceState

scripts/gen-store-assets.mjsWorks. Renders the modern popup in Chromium against a mocked chrome.* API and composites the store icon, 440×280 promo tile, and two 1280×800 screenshots into store/. Needs sharp + playwright installed --no-save, plus the Gelasio font.
store/listing.mdHolds every dashboard text field — name, summary, description, category, single purpose, three permission justifications, data-usage answers.
store/README.mdA six-step manual submission checklist and an asset→dashboard-field table.
store/privacy-policy.mdThe hostable policy. Its URL is pasted into the dashboard by hand.

CINone. The repo has no .github/ directory at all. This ticket introduces the first workflow.

2.1 Two live defects this ticket surfaces

  • clipboardWrite has no permission justification. public/manifest.json requests ["bookmarks", "clipboardWrite", "favicon", "storage"], but store/listing.md justifies only three of them — clipboardWrite (added by BMX-6, the Cmd+C copy shortcut) was never written up. An unjustified permission is a common review rejection. The verifier in §6 makes this class of drift impossible to ship again, and the build session fixes this instance.
  • The version can silently drift. package.json and public/manifest.json carry the same string with nothing checking it. Only the manifest's copy matters to the store, so a bump that misses the manifest produces an upload the API rejects — after the build has already run.

3. The shape of the change

One orchestrating script, three small modules it composes, a pure verifier, and a thin CI wrapper. All under bookmark-express-v3/.

bookmark-express-v3/
  scripts/
    release.mjs        NEW  orchestrator — the one command
    cws-api.mjs        NEW  Web Store API v2 client (auth, get, upload)
    listing.mjs        NEW  pure parser for store/listing.md
    version.mjs        NEW  pure version bump + package/manifest sync
    gen-store-assets.mjs    CHANGED — font preflight (§5.3)
  verify-release.mjs   NEW  pure release-readiness check
  package.json         CHANGED — release / verify:release scripts
.github/workflows/
  release-draft.yml    NEW  workflow_dispatch wrapper

The split exists so the parts that can be tested without a network, a build, or a browser are — matching how dev-build.mjs and verify-dev-build.mjs already divide pure transform from I/O in this project. listing.mjs and version.mjs are pure functions over strings; verify-release.mjs asserts against them and the real files; release.mjs and cws-api.mjs own all the side effects.

4. The release command

npm run release -- patch          # or minor | major | 10.3.0
npm run release -- patch --dry-run
npm run release -- patch --skip-assets

Stages, in order. Any stage failing aborts the whole run — nothing is uploaded and no half-state is left behind beyond files already written to disk (which the summary names).

  1. Preflight Working tree clean (override: --allow-dirty). Credentials present and parseable (§5.1). store/ holds every asset store/README.md's table declares. verify-release.mjs's checks all pass — the same assertions, run up front so a copy or permission problem stops the release before a build burns two minutes.
  2. Version Resolve the bump to a concrete semver, write it into both package.json and public/manifest.json. Then GET the item from the API and assert the new version is strictly greater than what is already published or drafted — the upload endpoint rejects a version that is not higher, and catching it here costs one request instead of a full build.
  3. Build & zip Shell out to npm run zip unchanged, so the uploaded artifact comes off exactly today's path (type-check → Vite prod build → zip -r from dist/). Assert bookmark-express-v3.zip exists afterwards and that the manifest.json inside it carries the version from stage 2 — this is the last point where a stale dist/ could still slip through.
  4. Store assets (skip with --skip-assets) Run scripts/gen-store-assets.mjs. Hash each store/*.png before and after and record which ones actually changed — that list drives the manual checklist in stage 7, so a release whose art is unchanged never asks anyone to re-upload identical images.
  5. Listing Parse store/listing.md and write one paste-ready plain-text file per dashboard field into store/dist/ (gitignored). Enforce the length limits and the manifest cross-check (§5.2).
  6. Upload (skipped under --dry-run) POST the zip to the v2 upload endpoint. Poll the returned operation until it settles. Never call publish. The new version lands as the item's draft; submitting for review stays a human's decision, made in the dashboard.
  7. Report Print the residual manual checklist — a dashboard deep link, the exact files to paste from (only fields whose text changed since the last release), the exact images to drag (only those from stage 4's changed list), and the reminder to click Submit for review. Also print the local files the run modified, since release.mjs deliberately does not commit (§7).

5. Details worth pinning down

5.1 Auth — service account

Signed off: service account, not an OAuth client + refresh token. It is a v2-only capability, it removes the refresh-token-expiry failure mode that makes the classic setup fragile in CI, and it needs no consent flow.

Configuration, read from the environment (a gitignored .env locally, repo secrets/vars in CI):

NameMeaning
CWS_SERVICE_ACCOUNT_JSONThe service-account key — accepted either as inline JSON or as a path to the key file, so the same variable works for a CI secret and a local file.
CWS_PUBLISHER_IDPublisher this item belongs to.
CWS_ITEM_IDThe 32-character Web Store item ID to upload against.

cws-api.mjs signs a JWT assertion with the key and exchanges it for an access token scoped to https://www.googleapis.com/auth/chromewebstore. Sign it with node:crypto's createSign('RSA-SHA256') rather than adding google-auth-library — it is roughly thirty lines and keeps this project's zero-dependency scripting habit intact (gen-store-assets.mjs and verify-dev-build.mjs set the same precedent). Cache the token for the run; it outlives a single release comfortably.

Endpoints the client needs — and only these:

GET  https://chromewebstore.googleapis.com/v2/publishers/{pub}/items/{item}
POST https://chromewebstore.googleapis.com/upload/v2/publishers/{pub}/items/{item}:upload

There is deliberately no publish wrapper. Not writing it is the safeguard: nothing in this codebase will be able to submit a release for review by accident.

Setup is a one-time human task, and it is a prerequisite for the build ticket to be testable end-to-end. Create a Google Cloud project, enable the Chrome Web Store API, create a service account and key, then add that service-account email under Account in the Developer Dashboard. Note the ceiling: a publisher can have exactly one service account. The build session should document these steps in store/README.md and should not assume it can perform them.

5.2 Listing: what "update our description" can actually mean

The API will not accept our description, so the achievable goal is different: make the copy trustworthy and paste-ready, so the manual step is mechanical rather than a place where mistakes enter.

listing.mjs parses store/listing.md's existing structure — fenced code blocks under bolded field headings — into a keyed object. The file's format does not change; it stays the human-editable source of truth. From that, the release writes:

store/dist/          # gitignored
  name.txt
  summary.txt
  description.txt
  single-purpose.txt
  permission-bookmarks.txt
  permission-clipboardWrite.txt
  permission-favicon.txt
  permission-storage.txt
  MANUAL.md          # the stage-7 checklist, as a file you can keep open

And enforces:

  • Length limits — name ≤ 75, summary ≤ 132, description ≤ 16,000. Keep these as named constants in one place in listing.mjs; the store has moved them before and will again.
  • Permission parity — the set of justification blocks in listing.md must equal manifest.json's permissions array exactly. Both directions: a permission with no justification fails, and a justification for a permission we no longer request fails too. This is the check that catches the clipboardWrite gap in §2.1.
  • Non-empty — every field the dashboard requires is present and not whitespace.

To make stage 7 able to say "only the description changed", the release records a hash per field in a committed store/.listing-state.json after a successful upload, and diffs against it on the next run. Small file, and it is what turns the manual step from "re-check eight fields" into "paste one".

5.3 Store assets: fail loudly instead of degrading quietly

gen-store-assets.mjs renders its headlines in Gelasio, and its current comment is explicit that without the font installed it falls back to a generic serif. That is fine for a human running it and watching the output; it is a trap for an automated release, which would happily commit visibly worse screenshots. Add a preflight: after the page loads, check the font is actually available (document.fonts.check) and abort with an actionable message — pointing at the existing install instructions in the file's header — rather than rendering with the fallback.

This is the only change to the generator. Its rendering, layout, and outputs are otherwise untouched.

5.4 Version sync

Signed off: the release owns the bump. version.mjs exports a pure nextVersion(current, bump) (accepting patch / minor / major or an explicit semver) and a pure syncManifest(manifestJson, version). release.mjs writes both files, preserving each file's existing formatting — four-space indent, trailing newline — so the diff is one line per file.

6. verify-release.mjs

A pure release-readiness check in the mould of verify-dev-build.mjs: no network, no build, no browser, collect all failures then exit non-zero. Runnable on its own (npm run verify:release) and called by both the release preflight and the CI workflow.

  • package.json and public/manifest.json versions are equal and valid semver.
  • store/listing.md parses, and every field is present, non-empty, and within its limit.
  • Justified permissions and manifest permissions match exactly, both directions (§5.2).
  • Every asset in store/README.md's table exists at the declared pixel size — read the dimensions straight out of the PNG IHDR header rather than adding an image dependency to a check that must stay dependency-free.
  • The listing's stated item name matches the manifest's name.

7. CI wrapper

.github/workflows/release-draft.yml — workflow_dispatch only. No push or tag trigger: a release that fires on its own is the opposite of what this ticket wants.

Inputs: bump (choice: patch / minor / major), skip_assets (boolean), dry_run (boolean). Secret: CWS_SERVICE_ACCOUNT_JSON. Variables: CWS_PUBLISHER_ID, CWS_ITEM_ID.

Steps: checkout → Node + npm ci → install sharp and playwright --no-save and the Gelasio font (unless skip_assets) → node scripts/release.mjs → upload the zip and any regenerated PNGs as workflow artifacts → push a release/vX.Y.Z branch with the version bump, regenerated assets, and listing state, and open a PR for it with gh (preinstalled on the runner, authenticated by GITHUB_TOKEN).

The workflow holds no release logic of its own — it installs the generator's dependencies, sets three environment variables, and calls the script. Everything it does is reproducible locally by running the same command.

Why the script never commits and the workflow does. Locally, release.mjs leaves its edits in the working tree and lists them, so you review the version bump and any regenerated art before committing — same as any other change in this repo. In CI there is nobody to review a dirty tree, so the wrapper turns those edits into a PR. Keeping the commit logic in the wrapper is what lets the script stay a pure build step.

8. Acceptance criteria

  • npm run release -- patch in bookmark-express-v3/ performs stages 1–7 of §4 end to end and finishes with the new version sitting as a draft on the Web Store item.
  • The release never submits for review. No code path in the repo calls the v2 publish endpoint, and no wrapper for it is written.
  • All Web Store calls target API v2 (chromewebstore.googleapis.com/v2) and authenticate with a service account. No v1 endpoint and no refresh-token path exists anywhere in the codebase.
  • After the run, package.json and public/manifest.json carry the same new version, and the manifest.json inside the uploaded zip carries it too.
  • A version that is not strictly greater than the item's current store version aborts the run before the build stage, with a message naming both versions.
  • The zip is produced by npm run zip unchanged — the packaging path is the one shipping today.
  • store/ is regenerated by default; --skip-assets skips it. gen-store-assets.mjs aborts with an actionable message if Gelasio is missing, instead of rendering with the fallback serif.
  • Every dashboard text field is emitted to store/dist/ as its own paste-ready .txt, and the run fails if any field is empty or over its limit.
  • The manifest's permissions and listing.md's justification blocks must match exactly in both directions, or the run fails. clipboardWrite gains the justification it is missing today (§2.1) as part of this ticket.
  • The final report names only the dashboard fields whose text actually changed and only the images whose bytes actually changed since the last successful release, plus the dashboard deep link and the Submit-for-review reminder.
  • --dry-run does everything except the upload, and says so.
  • node verify-release.mjs runs with no network, no build, and no browser, reports every failure rather than the first, and exits non-zero on any.
  • The workflow is workflow_dispatch-only, contains no release logic beyond installing dependencies and invoking the script, and opens a PR carrying the version bump and any regenerated assets.
  • Credentials never reach the repo: .env is gitignored, the service-account key is a CI secret, and no credential value is printed — including in error paths.
  • store/README.md and the project README.md describe the new flow, including the one-time service-account setup and the manual steps that remain.
  • npm run check and npm run build still pass, and no file under src/, public/ (other than the manifest's version string), or index.html / options.html is modified — the extension's behaviour is untouched by this ticket.

10. Out of scope & open questions

  • Out of scope — publishing or submitting for review. Signed off (§11). The automation stops at the draft; a human clicks Submit. Staged rollout, deployPercentage, and skipReview are all deliberately unused.
  • Out of scope — the other extensions. bookmark-express, bookmark-express-next, chrome-theme-star-gazer, super-small-view-switcher, and video-killer are untouched. Only bookmark-express-v3 has store assets and a zip script. Generalising the tooling across the monorepo is a separate ticket, and worth doing only if a second extension actually starts shipping.
  • Out of scope — hosting the privacy policy. privacy-policy.md is still published by hand and its URL pasted into the dashboard. Automating that means owning a deploy target, which this repo does not have.
  • Out of scope — CI for anything but releases. This ticket adds the repo's first workflow; it does not add test/lint CI for pull requests. Worth its own ticket now that .github/ will exist.
  • Open — which store item does v3 update? The original MV2 extension is live at item edgcdcdceojjbiebdbgmacecicaknjih, while store/README.md's checklist reads as a first-time "Add new item" submission. Whichever it is, it is a value of CWS_ITEM_ID, so it does not block the build — but if v3 has never been submitted, the first submission must be done by hand (v2 cannot create items, §1), and the automation is only exercisable from the release after that. The build session should confirm the item ID before claiming an end-to-end run.
  • Open — what happens to an already-submitted draft. Uploading while a previous submission is still under review is a state worth confirming against the real item. v2 offers cancelSubmission for it; this spec does not use it. If the build session finds an upload fails in that state, surfacing the API's error clearly is enough — do not automate cancelling someone's in-flight review.
